## Supported path and identity

The supported path is input validation/preflight → existing `run_agent`/provider interface and structured parser → actual Phase8 assessment → actual Phase9 run/history assessment → fixed mandatory controls → canonical report candidate → actual rendered-file QA → explicit local host release decision. CLI group `audit` exposes validate/run/inspect/review/release; exact flags are documented with implementation. No force/skip-control release option. Existing diagnostic commands and Phase7-only legacy releases are clearly distinguished and cannot pass the new canonical verifier.

Offline mode accepts only the built-in recorded provider with captured bytes, never provider-name resolution, subclasses/callbacks or network fallback. Its output still traverses the actual runner/parser/evaluator. Provider configuration and mode are captured honestly. Existing production provider interfaces remain usable integration boundaries; this task executes no live provider. A future live authorization is separate from any offline grant and historical experiment ledger.

A strict, versioned bundle contains the complete RunRecord (raw responses and original/review/adjudication layers), current selected analysis, fixed control decision, provenance manifest and rendered Markdown/HTML. Bind case identity to existing `case_key` (task ID, exact claim/context), run ID and full analysis/history fingerprints. Explicit valid human selection/correction uses `submit_human_review`; it creates a new revision with parent binding, never edits a released prior revision. All present history carriers must remain covered; missing/divergent history is not made authoritative by rendering or host intent.

Stable negative scientific decisions may be released if technical and mandatory controls pass. Scientific UNKNOWN remains distinct: material UNKNOWN requiring Phase9 review blocks release, while an explicitly nonmaterial unknown component remains visible in an otherwise complete report. Reviewer agreement or host intent cannot waive Phase8 controls or unresolved mandatory review. Original label, derived taxonomy, scientific state, execution, review and release are independent fields.

## Fixed controls / release authority

Control records have stable ID/version, exact subject fingerprint, execution state, eligible/evaluated population, findings and reason. Required set: input/preflight; parser/analysis completeness and source binding; all five existing Phase7 checks; Phase8 semantics/taxonomy; Phase9 history/mandatory review; provenance; actual Markdown and HTML post-render QA. Registry identity/count/version and every required control are checked by the boundary and verifier. Missing, duplicate, unknown, stale, failed, vacuous or unexecuted required controls block. A caller/model cannot provide an authoritative all-green dictionary or select only convenient checks. Recompute controls from bound raw/structured inputs at release/inspection, rather than trusting stored derived assertions.

Reuse the five existing gate functions and eligibility definitions. Claim/provenance/finding/client populations must be nonempty, bound and evaluated. No empty overall control set can pass. A genuinely inapplicable optional population (e.g. no client negative assertion for search-scope binding) is explicitly N/A with zero eligibility, a host-derived reason, and successful execution of the corresponding check without blocking findings. This follows existing AA-P8 applicability; AA-P10 versions this policy explicitly without modifying the stricter historical Phase7B official-release policy. Unknown applicability, skipped checks or fake N/A flags block. Scientific limits and all material findings remain visible.

Operational states: PREFLIGHT_BLOCKED, RUN_FAILED, ANALYSIS_INCOMPLETE, REVIEW_REQUIRED, RELEASE_BLOCKED, READY_FOR_RELEASE, RELEASED. READY is a checked candidate without host release intent. RELEASED is an explicit **local artifact** decision for the exact verified bundle, never truth, customer approval or software publication. CLI and every output share one current state. Controlled errors identify cause and a next step; no success based on process completion or renderer return alone. CLI exit 0 means requested operation completed in its declared supported state; 2 means a controlled blocked/incomplete state; 1 means technical/unexpected failure; usage errors follow Click. Docs must specify operation-specific meaning.

## Rendering, QA and provenance

A single deterministic semantic projection supplies all formats; no final prose generation/model calls and no new scientific renderer logic. Required visible sections: verbatim original claim; material propositions/IDs/derived judgments and composite; original label and derived taxonomy; bound evidence IDs/source IDs/quotes/type/direction; search scope and lack of external search; population/endpoint/product/inference limits; UNKNOWN; conflicts and all review/adjudication states; limitations; execution/release state; provenance. Summaries may only restate this projection without strengthening it. Full material fields remain available beyond any concise summary.

Markdown is the reference. HTML escapes all foreign claim/source strings, neutralizes active URLs/markup and clearly separates trusted status from quoted input. Both retain full ordered content, Unicode, long values, sources/warnings and history. No clipping, ellipsis, hidden essential panels or fixed print heights. Narrow layouts and print pagination must preserve essential material; long tables repeat headings or use a readable printable representation.

Post-render checks read the actual files. Validate expected sections/material values/links/warnings, semantic projection parity, encoding, ordering and absence of truncation; reject unexpected/missing/altered bytes against canonical render output. Both formats are mandatory. QA is bound to actual file hashes. Representative positive, negative/UNKNOWN/conflict and long/hostile-text outputs receive real browser screenshots and print pagination inspection before RC acceptance. Visual evidence states exact format, bytes, viewport/print method and result. These representative visual checks do not pretend every future report was manually inspected.

Final release uses staged final-status reports, actual-byte QA and atomic promotion; no unverified status rewrite after QA. Decision binds case/run/analysis, controls and report fingerprints. Manifest contains code version/fingerprint (and verified source commit when available), contract/config versions, actual provider/model/mode, input/evidence/ledger fingerprints, Phase8/9/review summaries, decisions, artifact hashes and timestamp. Every offline artifact is explicitly marked recorded/synthetic, never a fabricated live model snapshot. Avoid cycles: reports cite stable record/provenance core identity, decision binds reports, manifest binds record/decision/reports, manifest self-fingerprint excludes only its own fingerprint field. Verifier validates exact required file set/content, current bindings and decisions; altered/missing/mismatched artifacts cannot retain release. Hashes are integrity checks, not authentication against an actor rewriting code and all hashes; no PKI/IAM project.

## Work packages, evidence and stopping rules

WP10.1 owns canonical orchestration/object/status/provenance/CLI (10.1/10.2/10.8–10.10). WP10.2 completes semantic reports, MD/HTML/print and post-render QA (10.3–10.7). WP10.3 completes clean installation, docs, local RC and integrated acceptance (10.11–10.14). Intermediate missing format/QA stages remain fail-closed; no fabricated release while a required stage is unimplemented.

Exactly two reused agents: implementer Astra High, critic Astra Extra High; coordinator continues accepted Astra Extra High session. Backends/settings not independently queryable; document assigned roles without claiming extra verification. Single writer per file. Critic reads actual diff/results, writes no production/tests/expectations. One contract critique before implementation; each WP first critique plus at most two correction/rechecks. Material remaining error at limit → PARTIAL/BLOCKED, no extra agents/subpackages/reset. Final report critique checks evidence, not a new general code audit.

Before declared acceptance, freeze a small versioned corpus and expectations/hash, distinct from development tests and future efficacy holdout. Cover positive release; bounded negative release; material UNKNOWN/review block; optional unknown visibility; missing/vacuous/stale/bypassed controls; Phase8/source failure; case/manifest/report tampering; human history preservation; durable variant/budget limits; offline provider isolation; real MD/HTML parity/escaping/long output; malformed rendering; replay with zero extra calls. Test controls must include successful valid paths, not blanket rejection.

Use the unchanged 2290-test Phase9 baseline with targeted connections, not a fresh full baseline suite. Required final validation: new/affected lint, compileall, diff check; preserved existing lint baseline; one full suite after final integration, preferably on the isolated clean installed codecommit. Supported runtime initially Python >=3.11 per existing packaging; exact tested interpreter/platform recorded, broader matrix not invented. Installation dependencies/extras and browser-QA tooling must be declared. Clean reproduction uses only committed contents and a fresh environment, no developer PYTHONPATH/.venv/ignored fixtures. Package examples must ship or be tracked/documented inputs.

Permanent evidence lives under `analysis/phase10_validation/` (compact logs, checksums, screenshots/print evidence and reproduction manifest); /tmp may host scratch but is insufficient as final evidence. Exactly three task documents: this contract/matrix, phase10_review_journal.md and phase10_closeout.md. Product README/docs and machine evidence may be added. RC freeze records codecommit, versions/config/formats/results/limits; after freeze only material blocker corrections with explicit evidence updates. PHASE_10_PASS requires all mandatory criteria, package approvals, clean reproduction, actual visual/print checks, frozen acceptance and required tests. Then stop; live operations, empirical efficacy/fault-injection final validation and v1 publication need separate work orders.
